# 05 — Получать сведения о путях через платформенный адаптер

**Приоритет:** P2. **Статус:** ready-for-agent.

**Что сделать:** clipboard и drag/drop по-прежнему создают правильные ResourceDraft, но parsing/классификация в Application не вызывают File.Exists/Directory.Exists. Сведения о существовании и типе объекта предоставляются через отдельный порт.

**Блокируется:** ничем — можно начать сразу.

**Граница:** ResourceDraftFactory, асинхронный orchestrator импорта, порт path metadata и его адаптер; соответствующие callers. ResourceDraft и формат хранения сохранить. LaunchService, правила удаления и visual extraction не переписывать.

**Критерии приёмки:**

- [ ] Чистый parsing тестируется без файлов/каталогов; Application не вызывает filesystem APIs для проверки существования.
- [ ] Файл, каталог, executable/shortcut и image сохраняют текущие правила классификации.
- [ ] Явно заданный несуществующий путь и текст с embedded path сохраняют различие текущих режимов requireExisting.
- [ ] Недоступный путь даёт предсказуемый fallback/результат; исключение адаптера не падает в UI.
- [ ] Проверки пути выполняются вне UI thread; отмена предотвращает публикацию устаревшего результата. Для системного синхронного вызова нельзя обещать мгновенную физическую отмену.
- [ ] URL и свободный текст продолжают импортироваться без обязательной проверки filesystem.
- [ ] Clipboard/drop используют одну классификацию; запрос не повторяет одну и ту же проверку пути без необходимости.

**Проверка:** fake metadata для всех перечисленных случаев; отдельные тесты адаптера с временными файлами; build и ручной clipboard/drop. Задержку UNC-пути измерять отдельно, утверждение о текущем UI freeze считать гипотезой.
