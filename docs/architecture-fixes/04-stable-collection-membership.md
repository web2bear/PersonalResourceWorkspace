# 04 — Связать ресурсы с коллекциями по стабильному CollectionId

**Приоритет:** P2. **Статус:** ready-for-agent.

**Что сделать:** принадлежность ресурса определяется Guid коллекции с FK; переименование изменяет имя для отображения и не переписывает membership. Сейчас связь хранится через изменяемую строку Collection.

**Блокируется:** ничем — можно начать сразу.

**Граница:** одна завершённая миграция схемы, DTO/порты persistence и все затронутые входы/фильтры/навигация UI. Не создавать будущую модель membership/order/nested collections. Операции добавления и удаления адаптировать в том состоянии, в котором они существуют на момент интеграции; не реализовывать задачи 02/03 внутри этой задачи.

**Порядок внутри задачи:** расширить представление новым ID; заполнить его из существующих коллекций; перевести все callers и запросы; удалить зависимость принадлежности от имени после проверки. Промежуточная совместимость должна быть определена явно, постоянную двойную запись имени и ID не оставлять.

**Критерии приёмки:**

- [ ] Миграция существующей БД сохраняет ID ресурсов, содержимое, visual metadata, коллекции и количество записей.
- [ ] Сопоставление имён учитывает существующую SQLite-семантику COLLATE NOCASE.
- [ ] Ресурс с неизвестным CollectionId не сохраняется; включение FK проверено.
- [ ] Для старых orphan-ссылок задано детерминированное решение: миграция завершается диагностируемой ошибкой и rollback без удаления данных; исправление данных отдельным инструментом вне задачи.
- [ ] Rename не меняет CollectionId ресурса; фильтры, счётчики, корзина и navigation работают после рестарта.
- [ ] Move/delete сохраняют атомарность; активная коллекция не идентифицируется только именем.
- [ ] Повторный запуск миграций безопасен; ошибка преобразования оставляет исходные данные доступными.

**Проверка:** fixtures старой схемы, регистровые варианты и orphan-ссылка в временных БД; rename/move/delete; build App и ручной рестарт. Реальную пользовательскую БД для разработки не использовать.
